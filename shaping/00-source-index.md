# 来源索引与裁决顺序

## 为什么需要这份索引

仓库里同时存在 `mvp/`、`web/` 和 `uni/` 三套叙述。如果不先固定来源角色，后续写 PRD 时很容易把“Uni 当前没做”误写成“不需要做”，或者把旧 Web 的技术限制带进正式工程。

## 来源优先级

| 优先级 | 来源 | 用途 | 不应被误用为 |
| --- | --- | --- | --- |
| S1 | 用户明确说明 | 解释最终意图、裁决命名与范围 | 可被旧文档覆盖的“口头补充” |
| S2 | `mvp/` 当前实现 | 完整功能、页面行为和交互基线 | 推荐继续使用的工程架构 |
| S3 | `mvp/PRD.md` | 业务规则、数据对象、边界、场景 | 已全部实现的证明 |
| S4 | `mvp/styles.css` 与 `web/client/styles.css` | 用户认可的视觉语言和信息密度 | 必须逐行复用的 CSS |
| S5 | `uni/app/`、`uni/server/`、`uni/contracts/` | 正式工程能力、数据权威与当前实现事实 | 最终产品范围上限 |
| S6 | `uni/PRD.md` 与 `uni/docs/` | 当前 Uni 阶段的目标、架构和历史验收 | 可以覆盖用户新确认的完整目标 |
| S7 | 其余 README、历史记录与测试报告 | 解释演进、部署和验证条件 | 当前在线可用性的自动证明 |

## 三个版本的职责结论

| 版本 | 产品功能 | 视觉体验 | 工程实现 | 最终职责 |
| --- | --- | --- | --- | --- |
| MVP | 最完整 | 用户当前最认可 | 单机/localStorage 原型 | 目标产品与交互母版 |
| Web | 与 MVP 几乎相同 | 与 MVP 一致 | 增加 Web 包装和整包 JSON 同步 | 证明旧界面可 Web 化，但不是目标数据架构 |
| Uni | 当前功能较窄 | 用户明确不满意 | 身份、服务端数据、异步任务、私有存储和事务更强 | 唯一正式建设底座 |

## 事实核对摘要

- `CODE-VERIFIED`：MVP 与 Web 的主要前端脚本、样式保持同源，Web 没有重新定义一套完整产品。
- `CODE-VERIFIED`：Uni 已有登录/邀请、Demo 隔离、产品/计划/批次、今日/记录、精确撤销、异步识别、账户清理等正式工程能力。
- `CODE-VERIFIED`：Uni 尚未覆盖 MVP 的完整页面和领域能力，尤其是多成分确认、计划总览、成分日历/导出、成本账本 UI、AI、笔记和健康资料。
- `DOCUMENTED`：Uni 的历史集成/E2E 记录不能替代当前环境的实时生产验收。
- `CONFIRMED`：迁移目标是“用 Uni 工程实现 MVP 的完整产品思想，并恢复用户认可的视觉”，不是三选一。

## 冲突裁决流程

1. 先检查是否有用户明确结论；有则按 S1。
2. 没有时对照 MVP 代码与 MVP PRD；一致则进入目标合同。
3. 若代码和 PRD 不一致，记录到 `05-open-questions.md`，不自行猜测。
4. 再检查 Uni 是否已实现；已实现则尽量复用其领域模型和事务语义。
5. 若 Uni 实现改变了用户可见行为，必须在 PRD 中写出迁移与验收标准。
