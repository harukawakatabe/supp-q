# 视觉与交互基线

## 已确认结论

- `CONFIRMED`：用户认为 MVP/Web 的前端样式更顺眼，Uni 当前视觉不是目标。
- `CODE-VERIFIED`：`mvp/styles.css` 与 `web/client/styles.css` 当前 SHA-1 一致；两者可视为同一视觉基线。
- `CONFIRMED`：保持 MVP/Web 的视觉语言和信息层级，允许为触控、无障碍和真实状态反馈做有证据的适配修正。

## 可直接提取的设计语言

| 维度 | MVP/Web 事实 | 迁移要求 |
| --- | --- | --- |
| 画布 | `#f7f7f5` 背景，白色内容面；移动壳最大宽度 430px | H5 以移动端为主，桌面居中，不把页面拉成宽后台 |
| 字体 | Inter/SF/PingFang 优先；正文 14px、1.5 行高 | 保留高信息密度但保证中文可读性 |
| 主文本 | `#191919`，弱文本 `#6f6f6f` | 避免 Uni 当前若存在的过浅文字或大面积装饰色 |
| 边界 | `#e3e3e0` 细线，阴影克制 | 信息靠层级与分隔组织，不靠厚重卡片堆叠 |
| 圆角 | 基础半径 4px | 保留偏工具感、低圆角；不要默认套大圆角“健康 App”模板 |
| 主动作 | 黑色/近黑；弱动作使用 `#f1f1ef` | 主要操作数量要少，危险操作独立语义色 |
| 语义色 | 蓝、琥珀、橙、紫、绿、红均有 soft/border 三阶 | 用于时段、周期、提醒、风险，不用于无含义装饰 |
| 页面间距 | 页面左右 16px，上 24px，下方为底栏预留 104px | 维持紧凑节奏并适配安全区 |
| 标题 | 主标题 28px/700；eyebrow 13px | 大标题只负责定位页面，主体尽快进入任务信息 |
| 导航 | 五个高频任务常驻底部 | 恢复“记录/计划/添加/成分/补剂柜”的产品心智 |

## 信息层级约束

1. **今日先行动**：首屏优先呈现日期、进度和下一项，而不是欢迎语或品牌插画。
2. **列表先扫读**：产品名、剂量/时段、状态、余量和风险要形成稳定列位；避免每张卡片布局不同。
3. **复杂规则渐进展开**：默认显示当前结论，编辑或解释时再展开周期组合、证据和原始 OCR。
4. **状态靠文字加颜色**：不能只靠颜色区分成功、低置信、临期和错误。
5. **关键数值可追溯**：余量、预计耗尽、摄入总量旁应能进入来源或计算说明。
6. **一次只有一个主动作**：确认页的主动作是“确认产品”，详情页则按用户当前任务决定，不堆多个同权重按钮。

## 核心组件清单

后续前端不应逐页随意造样式，应先形成这些可复用组件：

- `AppShell`：430px 移动壳、背景和安全区。
- `TopBar`：eyebrow、标题、可选右侧操作。
- `BottomNav`：五个主入口、选中态、添加动作。
- `SectionHeader`：区块标题、摘要、辅助操作。
- `CompactCard`：低圆角、细边界、可扫描行布局。
- `StatusChip`：成功、处理中、低置信、暂停、临期、错误。
- `TimeSlotGroup`：早/中/下午/晚语义色与任务列表。
- `ProductRow`：产品、剂量、余量、风险、当前状态。
- `MetricPair`：标签/数值/单位，适合库存与成分。
- `EvidenceDisclosure`：原图、原文、译文、置信度、来源。
- `FormField` 与 `IngredientRows`：紧凑编辑、多行成分增删和单位。
- `InlineNotice`：降级、错误、手工继续与恢复建议。
- `EmptyState`：说明下一步，不用大型装饰插画替代操作。
- `ConfirmBar`：移动端固定主动作并处理安全区。

## 页面级迁移优先顺序

| 顺序 | 页面组 | 原因 |
| --- | --- | --- |
| 1 | AppShell、底栏、今日、补剂柜 | 先恢复用户每天看到的产品样貌与信息架构 |
| 2 | 添加、处理中、确认 | 同时解决最大功能缺口和最复杂状态 |
| 3 | 产品详情、计划、批次/成本 | 建立持续管理闭环 |
| 4 | 记录、成分日历、导出 | 用统一事实模型补齐回看与理解 |
| 5 | AI、笔记、健康资料、设置 | 安全边界确认后再完成低频入口 |

## 不应继承的旧实现限制

- 不复制 MVP/Web 的 localStorage 状态模型。
- 不用整份用户状态 JSON 覆盖服务端数据。
- 不把页面渲染时的大跨度日期循环直接搬进 Vue 响应式计算。
- 不因为追求像素一致而隐藏异步任务、网络失败、权限和重试等真实状态。
- 不把桌面鼠标交互原样套到触屏，点击目标和底部安全区必须重新验收。

## 视觉验收建议

每个页面组进入实现前，至少提供以下三栏对比：MVP/Web 基线截图、Uni 当前截图、拟实现稿。验收分别记录：

1. 信息是否齐全；
2. 层级和密度是否延续用户偏好；
3. 是否引入必要的工程状态；
4. 是否有未经确认的风格改造。

本文件从 2026-09-13 起作为后续设计与前端实现的视觉验收基线。
