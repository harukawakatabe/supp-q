# 规则与数据差距

## 总原则

迁移的难点不是把旧页面“接上接口”，而是让 MVP 的用户行为落到 Uni 的服务端事实模型，同时避免重复状态、历史漂移和 AI 越权。

## 规则对齐

| 领域规则 | 完整产品要求 | Uni 当前基础 | 差距/决定 |
| --- | --- | --- | --- |
| 三层计划 | 周规则、间隔天周期、长期服停周期取交集 | `READY` 核心算法和测试已存在 | 前端需解释组合结果；长期周期也需历史版本语义 |
| 历史计划 | 新规则只影响生效日之后，过去记录可重算/追溯 | `PARTIAL/STRONGER` 已有 day-cycle versions | 抽象为统一 schedule version，避免只保护一种周期 |
| 今日派生 | 指定日期任务从当日有效计划计算 | `READY` 基础存在 | 时区、跨日、时段与暂停/耗尽规则需写成契约 |
| 临时服用 | 不要求当天计划命中，但仍生成真实 intake | `PARTIAL` 服务端支持 ad hoc 语义 | 补前端入口及与成分聚合的统一处理 |
| 历史补录 | 使用用户选择的发生日期，库存事务发生在提交时 | `READY/PARTIAL` 基础存在 | 明确批次按发生日还是提交日排序；需在 PRD 裁决 |
| 防重复 | 网络重试不能重复创建 intake 或扣库存 | `STRONGER` 幂等/事务基础 | 客户端生成稳定幂等键并显示“已处理”结果 |
| FEFO | 有效期早者优先；可拆多个批次；不足则整笔失败 | `STRONGER` 已有事务分配 | 明确无有效期批次排序与并列规则 |
| 精确撤销 | 恢复原 intake 的每笔 allocation；重复撤销无副作用 | `STRONGER` 已实现 | 作为 100% 正确率门槛，不改成重新计算 |
| 数值精度 | 剂量、数量、单价和聚合不得受二进制浮点漂移 | `STRONGER` 后端有固定精度基础 | API 和前端展示必须保留精度/舍入规则 |
| 耗尽预测 | 基于未来有效计划和当前库存推算 | `READY/PARTIAL` 已有预计耗尽/最晚启用基础 | 纳入计划版本、暂停、无库存和区间上限状态 |
| 临期风险 | 结合有效期、预计消耗与阈值 | `PARTIAL` 有批次和阈值基础 | 形成确定性风险枚举和解释文案 |
| 成本 | 批次总价/单位成本跟随 allocation 形成实际消耗成本 | `PARTIAL` 已保存 price 与 allocation unit cost | 明确币种、退款/调整、舍入、库存价值口径 |
| 成分聚合 | 从有效 intake × 已确认产品成分派生，并加手工记录 | `MISSING` | 不能保存一个独立“今日汇总真相”与 intake 打架 |
| 单位换算 | 兼容质量单位换算；IU 仅在有成分特定因子时换算 | `MISSING` | 换算表要版本化、注明来源；不可换算则分开展示 |
| 同义名 | 同一成分的英文、中文、别名映射到标准实体 | `MISSING` | 保留原始名称，映射可人工修正且影响范围可见 |
| 提醒 | 由计划和风险派生，可有全局默认与单品覆盖 | `PARTIAL` 当前主要保存 reminder times | 外部渠道、权限和送达策略由 Q4 确认 |
| AI | 只能解释已确认事实和明确参考，不写回确定性结果 | `MISSING` | Q2/Q3、数据最小化、引用和评测通过后实现 |

## 目标领域对象

### Uni 已有且应继续作为权威

- User、Workspace、Session、Invitation。
- Product、ProductIngredient、ProductSchedule、DayCycleVersion。
- InventoryBatch、IntakeRecord、IntakeAllocation、InventoryEvent。
- FileObject、RecognitionSet、RecognitionJob、RecognitionEvidence。
- AccountCleanupJob、WorkerHeartbeat 等运行对象。

| 对象 | 目的 | 关键字段/约束 |
| --- | --- | --- |
| ScheduleVersion | 统一保护全部计划历史 | 生效区间、周规则、日周期、长周期、时段、餐食、来源版本 |
| IngredientAlias | 标准化中英文和品牌写法 | 原名、标准成分、语言、置信/人工确认、版本 |

| ReminderPreference | 全局默认和单品覆盖 | 类型、渠道、时间、权限状态、时区、启停 |
| ProductNote | 个人经验沉淀 | 产品关联、正文、来源、创建/修改时间 |
| AiThread/AiMessage | 受控解释会话 | 关联对象、输入快照、引用、模型、边界结果、成本 |

| ExportJob | 大范围导出 | 范围、字段、时区、状态、文件、过期时间 |

## 识别到产品的映射问题

Uni 当前最大的结构性风险是：识别任务可以产生丰富字段，但新增页把 `ingredientsZh` 或 `ingredientsRaw` 截取为最多 80 个字符，填进一个 `ingredientName`，最终仅在含量大于 0 时保存一条成分。这会同时造成：

1. 多成分丢失；
2. 原文、译文和结构化成分混为一列；
3. 识别证据无法回溯到具体字段；
4. 成分日历未来无法可靠聚合；
5. 用户以为“确认过”但数据库实际没有保存完整事实。

因此后续 PRD 必须先定义 `RecognitionCandidate -> ConfirmationDraft -> Product/Ingredient/Batch/Schedule` 的逐字段映射，再改确认页。不能继续在现有单成分表单上追加零散字段。

## 单一事实来源

| 用户看到的结果 | 权威来源 |
| --- | --- |
| 今天该服什么 | 指定日期有效的计划版本 + 产品状态 |
| 今天是否完成 | 有效 intake 记录，不是页面本地勾选 |
| 当前库存 | 批次初始/调整 + allocation/event 账本 |
| 撤销后库存 | 原 intake allocations 的反向事务 |
| 当日成分摄入 | 有效 intake × 当时适用的已确认成分版本 + 手工成分记录 |
| 预计耗尽/临期 | 库存批次 + 未来计划 + 风险规则 |
| AI 上下文 | 用户授权的确认数据快照；模型回复不是事实源 |

## 必须在 Make-PRD 中形成的契约

1. 产品确认事务究竟一次创建哪些对象，部分失败如何回滚。
2. 成分编辑是否影响历史摄入聚合，若不影响则成分也需要版本。
3. 补录的 FEFO 排序依据，以及修改/撤销补录的账本行为。
4. 产品停用、耗尽和删除对未来任务、历史、AI 与导出的影响。
5. 所有日期/时区的存储与展示规范。
6. 识别候选、人工确认值和后续编辑值的溯源方式。
7. 成本账本和成分换算的精度、舍入、版本与来源。
8. AI 可读字段、不可回答问题、引用要求、失败降级和费用控制。
